# claws

claws is a verifiable C++ subset modeled on Bend 2's Laws. `DESIGN.md`
has the design, the milestones, and the lessons behind every rule here.

## Who owns which file

In each project under `examples/`:

- `code.hpp` is the claws subset. The AI may change it.
- `main.cpp` is the driver, outside the subset. The AI may change it.
- `Code.lean` is generated by claws-lean from `code.hpp`. Never edit it.
- `Ast.lean` is generated by claws-ast from `code.hpp`: the program as
  the semantics in `lean/Claws/Sem.lean` sees it, and a validation law
  `Laws.Valid.f` for each function. Never edit it.
- `LAWS.lean` states the laws. A human writes it. The AI must not edit
  it, and must not weaken a law to make it provable. If a law looks wrong,
  say so and stop.
- `Verdict.lean` is the gate. A human owns it. Never edit it.
- `PROOF.lean` proves the laws and the safety obligations. The AI writes
  it.

## The gate

Run `scripts/gate.sh examples/<Project>` after any change to `code.hpp` or
`PROOF.lean`. Work is done only when it prints ALL PROOFS CHECK, the
differential test reports that C++ and Lean agree, and the program runs.
A `sorry` is never done: the verdict reports it as SORRY.

If the differential test reports a disagreement, the translator
(`tools/claws-lean`) has a bug, since the proofs are about its output.
Report it with the differing line; never change a proof or a law to work
around it.

When `PROOF.lean` imports `<Project>.Ast`, the verdict requires every
validation law. Prove each with one command, `claws_valid f [Code.f]`,
after the functions f calls: a caller uses each callee's validation
instead of running its body again. A validation law that fails
with a counterexample means the translation differs from the C++: the
same kind of translator bug the differential test finds, and reported
the same way. `lean/Claws/Sem.lean` is part of the trusted base, so
change it only to cover more of C++, and cite the clause of the
standard each rule follows. `scripts/diff.sh examples/<Project> <cases> <seed>` runs a
larger test on its own.

## When a law fails

A counterexample to a proof step is not yet a counterexample to a law.
The step may fail because the invariant in `PROOF.lean` is too weak,
even though no real run reaches the values it reports. Find out which:
build an input that reaches those values and run it through `main.cpp`.
If the program breaks the law, the code is wrong. If no input reaches
them, strengthen the invariant.

If the code is wrong because the request itself conflicts with a law,
do not commit, and do not stop at "this is impossible". Report the input
that breaks the law, then offer changes to `code.hpp` that meet the
request while keeping every law true. Changing the law instead is the
owner's choice, never the AI's.
Incident: the diagonal moves trial (DESIGN.md, "An agent trial"), where
a down-right step from (11, 7) wrapped into the sealed room.

## Rules for writing PROOF.lean

These come from proofs that broke for the wrong reason. A proof that
breaks when the code changes shape, rather than when a law stops holding,
makes every refactor look like a bug and hides the real one.

1. Never write a proof that depends on the shape of the code. Do not
   count branches with a fixed `split <;> split`. Write `repeat' split`
   (or `split <;> (try split)`) and close every resulting goal with the
   same tactic, such as `all_goals bv_decide` or `all_goals bv_omega`.
   Wrap every normalizing step in `try`, as in
   `all_goals (try simp only [...] at *)`, since after a refactor a
   branch may have nothing left to rewrite, and a `simp` that makes no
   progress is an error.
   Incidents: Stats `record` (milestone 3), Bank `transfer_cases`
   (milestone 5), Bits `Safety.mean` (milestone 6), Vectors `bucket_lt`
   (milestone 7, which broke on `simp` making no progress once the code
   had no branch left).

2. Prefer tactics that produce counterexamples. `bv_decide`, `bv_omega`
   and `omega` report concrete values when a claim is false, which tells
   whoever reads the failure what broke. Structural tactics (`split`,
   `rfl`, `exact` with a guessed term) only say that a step failed. Use
   `bv_decide` on any goal that is purely about `BitVec` values, including
   `f.safe` functions.

3. Close impossible branches by contradiction, not by computation:
   `first | rfl | (exfalso; bv_omega)`. A branch that cannot happen should
   still be handled by the same uniform tactic as the rest.

4. Unfold `BitVec.ult` and `BitVec.ule` before `bv_omega` when a branch
   hypothesis is a Bool comparison:
   `simp only [BitVec.ult, BitVec.ule, decide_eq_true_eq] at *`. Do this
   after choosing a branch, not with `at *` before `exact`, which can
   rewrite the goal out from under it.

5. Prove loops with `fun_induction f.loopN ...`. State the invariant for
   any counter at most the bound (`i ≤ n → ...`), then apply it at the
   starting counter. Name the generated variables with `rename_i` in
   every case, including the exit case, rather than relying on
   inaccessible names.

6. Write literals as Lean numerals (`0`, `1`, `0xFFFF`). Generated code
   writes `(n : BitVec 32)`, which matches. Never write `0#32`.

7. Qualify C++ names that clash with Lean's, such as `Code.min` and
   `Code.max`, whenever `open <Project>.Code` would make them ambiguous.

8. For natural number arithmetic with a product of two variables, state
   the product the same way round everywhere (`q * b`, never also
   `b * q`), so `omega` treats it as one unknown. Use `grind` for ring
   identities on `BitVec`, such as `2 * (s + i) + n * (n - 1)`.

9. Before `bv_decide`, reduce field projections of structure literals
   with `all_goals (try dsimp only at *)`; otherwise `bv_decide` treats
   `{ x := a, ... }.x` as an unknown and reports a spurious
   counterexample. Do not run `simp_all` before `bv_decide`: it rewrites
   hypotheses with each other into forms `bv_decide` cannot use, which
   shows up as a counterexample at a point the hypotheses rule out.
   Incident: Game `step_safe` (milestone 9).

10. To unfold a constant that appears inside an `if` condition, use full
    `simp [..]`, not `simp only [..]`, which can rewrite the condition
    without its decidability instance and leave the term ill typed.
    Incident: Game `step_safe` (milestone 9).

11. Prove a safety obligation `Laws.Safety.f` as `theorem Safety.f` in the
   `Proof` namespace. If one cannot be proved, the C++ has a real
   problem: add a `claws::expects` to the function or a check to the
   caller. Never weaken the obligation.

12. Never put a lemma name you have not seen compile inside `try`. An
    unknown name makes the whole `simp` fail, `try` swallows the error,
    and the step silently does nothing. Incident: Utf8, where `not_not`
    (Mathlib) stood in for `Decidable.not_not`.

13. Split before unfolding constants. Unfold the function, `repeat'
    split`, and only then unfold the constants, in the hypotheses
    (`simp only [c1, c2] at *`). Unfolding a constant inside an `if`
    condition first can stop `split` from using the condition. This
    sharpens rule 10. Incident: Utf8 `rune_len_encode`.

14. For a function without loops, try no splitting at all: rewrite each
    lookup table read into a description of its index (prove
    `table[b.toNat]! = spec b` by `decide`, which checks every entry),
    turn each comparison with a size into a BitVec comparison, and run
    `bv_decide` on the whole goal. Leave `BitVec.ult` and `BitVec.ule`
    folded for `bv_decide`, which understands them (rule 4 is for
    `bv_omega`), and `clear` any hypothesis with a `∀` before it.
    Incident: the Utf8 safety obligations, four lines each this way.

15. `bv_decide` treats two terms as the same unknown only if they are
    written the same way: `p[(pos + 1).toNat]!` and `p[pos.toNat + 1]!`
    are unrelated to it, and so are a shift by `(4 : BitVec 32)` and a
    shift by the Nat 4. Rewrite every read into the form the code writes
    before calling it. Incident: Utf8 `decode_sound`.
